# Static Frontend CI/CD Project for SUT SE Lab

لینک استقرار پروژه (GitHub Pages): [لینک پروژه خود را اینجا بگذارید]

## گزارش پیاده‌سازی
در این پروژه از ۳ شاخه (Branch) مجزا استفاده شد:
- `main`: شاخه اصلی و محافظت‌شده که فقط از طریق PR آپدیت می‌شود.
- `dev`: شاخه توسعه که تمام فیچرها ابتدا در آن تجمیع شدند.
- `feature/navbar` و `hotfix/ui`: برای توسعه کامپوننت‌ها و رفع باگ‌ها.

در طول توسعه بیش از ۲۰ کامیت معنادار ثبت شد و ۲ کانفلیکت (هنگام ادغام feature در dev و hotfix در dev) به صورت دستی برطرف گردید. استقرار پروژه نیز توسط Github Actions روی Github Pages به صورت خودکار انجام شده است.

## پاسخ به پرسش‌ها

**۱. پوشه‌ی .git چیست؟ چه اطلاعاتی در آن ذخیره می‌شود؟ با چه دستوری ساخته می‌شود؟**
پوشه `.git` قلب تپنده مخزن گیت است و حاوی تمام تاریخچه پروژه، تنظیمات، اطلاعات شاخه‌ها (branches)، کامیت‌ها و آبجکت‌های گیت است. این پوشه یک دیتابیس کامل از سیستم کنترل نسخه محلی است و با اجرای دستور `git init` در یک دایرکتوری ایجاد می‌شود.

**۲. منظور از atomic بودن در atomic commit و atomic pull-request چیست؟**
اتمیک بودن به این معناست که هر کامیت یا PR باید تنها شامل یک تغییر منطقی، مستقل و کامل باشد. یعنی اگر آن کامیت را حذف (Revert) کنیم، پروژه دچار خطای کامپایل یا مشکلات پیش‌بینی نشده نشود. این کار باعث خوانایی تاریخچه گیت و راحت‌تر شدن فرآیند Code Review و Debugging می‌شود.

**۳. تفاوت دستورهای fetch و pull و merge و rebase و cherry-pick:**
- `fetch`: اطلاعات و تاریخچه جدید را از مخزن ریموت دانلود می‌کند اما تغییری در فایل‌های کاری شما (Working Tree) ایجاد نمی‌کند.
- `pull`: ترکیب `fetch` و `merge` است؛ یعنی علاوه بر دانلود تغییرات ریموت، آن‌ها را با شاخه فعلی شما ادغام می‌کند.
- `merge`: دو شاخه مختلف را با هم ترکیب می‌کند و یک "Merge Commit" جدید می‌سازد (تاریخچه هر دو شاخه حفظ می‌شود).
- `rebase`: پایه (Base) یک شاخه را تغییر می‌دهد؛ یعنی کامیت‌های شاخه فعلی را برمی‌دارد و روی آخرین کامیت شاخه هدف قرار می‌دهد تا تاریخچه خطی و تمیزتر شود.
- `cherry-pick`: یک کامیت خاص را از یک شاخه دیگر انتخاب کرده و فقط همان یک کامیت را روی شاخه فعلی اعمال می‌کند.

**۴. تفاوت دستورهای reset و revert و restore و switch و checkout:**
- `reset`: اشاره‌گر شاخه (HEAD) را به یک کامیت قبلی برمی‌گرداند (می‌تواند تغییرات را پاک کند یا در استیج نگه دارد). تاریخچه را بازنویسی می‌کند.
- `revert`: یک کامیت جدید می‌سازد که تغییرات کامیت‌های قبلی را خنثی (Undo) می‌کند. (بهترین روش برای خنثی کردن تغییرات در شاخه‌های عمومی بدون دستکاری تاریخچه).
- `restore`: برای برگرداندن تغییرات فایل‌ها در Working Directory یا Unstage کردن فایل‌ها استفاده می‌شود (جایگزین ایمن‌ترِ برخی کاربردهای checkout).
- `switch`: صرفاً برای تغییر دادن (جابجایی) بین شاخه‌ها استفاده می‌شود.
- `checkout`: دستور قدیمی‌تر و همه‌کاره که هم برای جابجایی بین شاخه‌ها و هم برای برگرداندن فایل‌ها به حالت قبل استفاده می‌شد (در نسخه‌های جدید گیت به switch و restore تفکیک شده است).

**۵. منظور از stage یا همان index چیست؟ دستور stash چه کاری را انجام می‌دهد؟**
- **Stage (Index):** یک محیط واسط (ایستگاه بازرسی) بین Working Directory و Repository است. فایل‌هایی که تغییر کرده‌اند ابتدا به این محیط اضافه می‌شوند (`git add`) تا در کامیت بعدی ثبت شوند.
- **Stash:** فضایی موقتی است برای ذخیره تغییرات فعلی (که هنوز کامیت نشده‌اند). با `git stash` محیط کاری شما تمیز می‌شود تا بتوانید به شاخه دیگری بروید و بعداً با `git stash pop` تغییراتتان را برگردانید.

**۶. مفهوم snapshot به چه معناست؟ ارتباط آن با commit چیست؟**
گیت برخلاف سیستم‌های قدیمی (مثل SVN) که تغییرات خط‌به‌خط (Diff) را ذخیره می‌کردند، در هر کامیت یک تصویر کامل (Snapshot) از وضعیت کل فایل‌های پروژه در آن لحظه ذخیره می‌کند. اگر فایلی تغییر نکرده باشد، گیت فایل را دوباره ذخیره نمی‌کند، بلکه به فایل قبلی لینک می‌دهد. کامیت‌ها در واقع اشاره‌گرهایی به این Snapshot ها هستند.

**۷. تفاوت‌های local repository و remote repository:**
- **Local Repository:** مخزنی است که روی سیستم شخصی شما قرار دارد (درون پوشه `.git`) و تمام عملیات مثل کامیت، تغییر شاخه و ... روی آن به صورت آفلاین و بسیار سریع انجام می‌شود.
- **Remote Repository:** مخزنی است که روی یک سرور راه دور (مثل GitHub یا GitLab) قرار دارد و برای اشتراک‌گذاری کد، کار تیمی و بک‌آپ‌گیری استفاده می‌شود. هماهنگی بین این دو از طریق push و pull انجام می‌شود.
